# AGENTS.md

This file provides guidance to Codex (Codex.ai/code) when working with code in this repository.

## Workflow

- After making changes, check for any bugs, make fixes, and then commit the changes to main when done.
- The browser/WebGL app under `src/` is the visual and behavioral source of truth. Native implementations live under `macos/MatrixCodeScreenSaver/` (Objective-C/AppKit/Metal), `windows/MatrixCode/` (C++20/Win32/Direct3D 11), and `linux/MatrixCode/` (C++20/Qt/OpenGL). Whenever a feature, behavior, bug fix, configuration change, token/countdown/image rule, or visual tuning change is made to one implementation, make the equivalent change to the other applicable implementations in the same workstream so all four stay aligned. If exact parity is impossible, document the intentional difference in the relevant README and tests.
- Wallpaper Engine is a web-wallpaper distribution of the browser app, not another native renderer. Host-property or lifecycle changes belong in `src/platform/wallpaperEngine.ts`, the canonical catalog in `wallpaper-engine/property-spec.json`, generated `wallpaper-engine/project.json`, and the package tests/docs as applicable.

## Commands

- `npm run dev` — Vite dev server (port 5188, registered with LanternPad; assume it is already running).
- `npm run build` — type-checks (`tsc --noEmit`) then builds a single inlined `matrixcode.html` via `vite-plugin-singlefile`.
- `npm run build:wallpaper` — builds the browser artifact and packages an offline Wallpaper Engine web wallpaper in `dist/wallpaper-engine/`.
- `npm run verify:wallpaper` — checks that generated `wallpaper-engine/project.json` matches the canonical property catalog.
- `npm run preview` — serve the production build.
- `npm test` — run the Vitest suite once. `npm run test:watch` for watch mode.
- Run a single test: `npx vitest run test/rainSim.test.ts` (or `-t "<name>"` to filter by test name).
- Native macOS screen saver: from `macos/MatrixCodeScreenSaver`, run `./test.sh`, `./build.sh`, and `./install.sh` as needed. The native project is generated by XcodeGen from `project.yml` and builds an Apple-Silicon `Matrix Code.saver` bundle.
- Native Windows: `npm run build:windows` stages an x64 Release app/`.scr` without tests; `npm run test:windows` builds x64 Debug and runs native tests; `npm run verify:windows` also creates the deterministic WARP capture; `npm run release:windows` builds x64/ARM64 MSI, portable, symbol, and checksum artifacts. These require Windows, Visual Studio 2022 with Desktop C++, and CMake 3.29+; release packaging also requires WiX v4. Signing is optional unless `-RequireSigning` is passed through to `Build-Release.ps1`.
- Native Ubuntu: `npm run build:linux` builds the Release Qt/OpenGL app; `npm run test:linux` builds Debug and runs the shared native and Linux platform suites; `npm run verify:linux` runs both; `npm run release:linux` creates the architecture-native Debian package. The Ubuntu 24.04 baseline requires Qt 6 development packages, OpenGL/EGL development headers, Ninja, and CMake 3.28+.

Web tests run in a Node environment (no DOM) and cover the headless simulation, glyph set, overlap-lane/adaptive-resolution controllers, message/intro logic, the portable image contract, and Wallpaper Engine host/package behavior. Native suites live under each platform project and must be run on their supported OS/toolchain.

## Architecture

A full-viewport WebGL2 Matrix digital rain, bundled into one self-contained HTML file. Entry: `src/main.ts` → `mountMatrixRain(container)` in `src/app.ts`, which wires everything together and owns the RAF loop, resize/visibility/fullscreen handling, WebGL context loss/restore, and the overlap-lane/adaptive-resolution controllers described below. Normal RAF elapsed time is split by `src/sim/frameSteps.ts` into bounded simulation substeps so low render FPS does not slow the rain and make it appear to accelerate when adaptive resolution recovers.

The rendering model is film-accurate: glyphs sit on a **stationary grid** and a wave of illumination sweeps down each column, leaving an exponentially decaying trail — the grid does not scroll.

Data flows in one direction each frame:

1. **`src/sim/rainSim.ts`** — `RainSim`, a deterministic, headless CPU simulation over a `cols × rows` grid. Packs per-cell state (brightness, glyph index, phase, head flags) into an RGBA8 `Uint8Array` (`state`). Channel layout and flag bits are defined in `src/types.ts`. Being DOM-free and seedable (`src/util/rng.ts`), it is fully unit-testable. Above density 20, `app.ts` runs several independent `RainSim` layers ("lanes") offset to fractional column positions and composites them additively so drops interleave between whole columns; `src/sim/overlapLanes.ts` is the pure, unit-tested module mapping density/tier to that set of lanes (it never touches `RainSim` itself, so the core sim's golden-file determinism is untouched).
2. **`src/gl/stateTexture.ts`** — uploads each lane's byte array as a texture every frame.
3. **`src/sim/imageScheduler.ts` / `src/sim/imageReveal.ts`** — schedules imported image masks on a separate deterministic hash timeline and builds per-cell image influence without perturbing rain or message RNG.
4. **`src/gl/renderer.ts`** — `Renderer` draws glyphs sampling the atlas + state texture(s), composites message/image influence, then runs a multi-level bloom post-process (brightpass → blur → composite, with scanline/vignette). Bloom level count scales with the quality tier (`low`/`med`/`high`). The actual render-target resolution is separately scaled by `src/gl/adaptiveResolution.ts`, a pure/tested EMA+hysteresis controller that lowers resolution under sustained frame-time pressure and restores it when headroom returns. Shaders live in `src/gl/shaders/*.glsl`, imported as raw strings via Vite's `?raw`. Uses `twgl.js` for GL boilerplate.
5. **`src/gl/glyphAtlas.ts`** — rasterizes the glyph set (`src/sim/glyphSet.ts`) into a texture atlas; rebuilt when the `mirror` control changes.

**Fallback:** if WebGL2 is unavailable or GPU init throws, `src/fallback/canvas2dRain.ts` runs a simpler Canvas2D rain and a compatibility notice is shown.

**Configuration & state:** `ControlsStore` (`src/config/controls.ts`) is an observable store of user-facing settings; `app.ts` subscribes to react to changes (e.g. `glyphScale` recomputes the grid, `mirror` rebuilds the atlas). Static tuning lives in `src/config/simConfig.ts`; color themes in `src/config/colorPresets.ts`. Other persisted docs (intro, messages, images, countdown) follow the same pattern — a `DEFAULT_*` value, a `sanitize*`/`clone*` pair built on the shared coercion helpers in `src/config/sanitize.ts` (`num`/`text`/`bool`/`capArray`), and a `localStorage`-backed store.

**Image reveals:** `src/config/imagesStore.ts` owns the portable `mx-images` document: at most 64 masks, each at most 96 × 96 cells, with standard padded Base64 containing exactly one greyscale byte per cell. `src/sim/imageMask.ts` aspect-fits imports without upscaling and preserves the established alpha-squared edge treatment. `ImageScheduler` independently selects images and placement and drives appear/hold/disappear, flicker, and brightness-fade envelopes. `imageReveal.ts` defines bilinear mask sampling, contrast/brightness signal, edge feather, virtual-grid placement, falling-rain gate, cell identity, and glyph selection. These constants and rounding rules are cross-platform contracts; change them in web, macOS, and Windows together with fixtures/tests.

**Overlays:** `src/ui/controlsPanel.ts` is the settings UI (toggle with `H`); `F` toggles fullscreen. Two text surfaces share one typing engine and token resolver:
- **Intro** — `src/sim/messageOverlay.ts` is the pure typing timeline (`MessageLine`/`TypeConfig`) plus its thin DOM renderer; while enabled it plays on every load, and `Escape`/click skips it. `src/config/introStore.ts` holds the user-editable script (lines, timing, whether rain falls during vs. after the intro); `src/sim/introRain.ts` computes the load-time density ramp-up (`densityRampFactor`/`loadRampMs`) so rain builds in smoothly both on the intro and on ordinary reloads. Edited via `src/ui/introEditor.ts` (`I` shortcut).
- **In-rain messages** — periodic phrases rendered as rain glyphs. `src/config/messagesStore.ts` holds the list, frequency, appear/hold/disappear timing, vertical position/jitter, and flicker/fade options; `src/sim/messageScheduler.ts` (`MessageScheduler`) times and jitters their appearance against a `RainSim`-shaped `MessageSink`. The scheduler optionally accepts rectangular `MessageRegion`s: normal rendering uses one full-grid region, while multi-monitor mode can place the same message independently inside each physical display slice. Edited via `src/ui/messagesEditor.ts` (`M` shortcut); `N` toggles messages on/off.
- **Images** — `src/ui/imagesEditor.ts` imports images into portable masks and edits their schedule/placement; `X` opens the editor and `Shift-X` toggles reveals. Images are positioned in full virtual-grid coordinates so a reveal remains continuous across browser multi-monitor slices.

Both surfaces resolve their tokens through one path: `src/sim/tokens.ts`, a pure/tested resolver driven by an injected `TokenContext`. Supported forms include `{name}`, `{greeting}`, `{time}`, `{time:fmt}`, `{countdown}`, `{countup}`, and named `{countdown:NAME}` / `{countup:NAME}` moments. Countdown/countup targets are persisted by `src/config/countdownStore.ts` and edited via `src/ui/countdownEditor.ts`. `src/ui/modalKit.ts`'s `ModalEditor` base class supplies the shared backdrop/dialog/Escape/reorderable-list scaffolding for the intro/messages/countdown editors, styled by the `.mx-modal*`/`.mx-line*`/`.mx-field` classes in `src/styles.css`.

`src/ui/favicon.ts` renders a live, theme-coloured favicon (three staggered rain columns) recoloured whenever the active preset changes.

**Multi-monitor mode (`src/multimonitor/`):** the Multi-monitor button (or triple-click shortcut) spans the rain across every monitor — one fullscreen window per display, each rendering a slice of one shared virtual grid so the rain is continuous across the physical arrangement. `multiMonitorGrid.ts` is the pure, unit-tested geometry (virtual grid + per-screen slices + slice extraction + fixed-timestep stepping); `multiMonitorFullscreen.ts` orchestrates it via the Chromium Window Management API (`getScreenDetails` / `requestFullscreen({ screen })`), opening per-screen windows that carry the session's vignette-derived message-placement mode and their own slice in the URL hash. Windows stay in lockstep with no per-frame messaging by running deterministic sims and message schedulers against a shared seed + `Date.now()` epoch; each window reloads the persisted message document when entering multi-monitor mode so the controller and fresh panels cannot diverge, and a `BroadcastChannel` only coordinates exit. With vignette off, an in-rain message is centered once in the full virtual grid; with any vignette applied, each window targets a copy inside its own physical slice. Message-only scramble uses a separate RNG so these local targets do not perturb the shared rain motion. Chromium-only; degrades to ordinary fullscreen otherwise. See `docs/multimonitor-setup.md`.

Reduced-motion (`prefers-reduced-motion`) and page-visibility are respected — the loop stops and renders a single static frame instead of animating.

## Wallpaper Engine web wallpaper

`src/main.ts` installs `src/platform/wallpaperEngine.ts` before mounting the app. The adapter queues callbacks that arrive before attachment, retains initial property state across changed-only deltas, maps fixed property slots into ordinary app documents, accepts a deterministically sorted/bounded image directory, applies the host FPS limiter, and freezes app-relative timelines while paused. Hosted mode uses in-memory stores and suppresses browser settings, fullscreen, and multi-window controls. The Canvas2D fallback must honor the same property, FPS, pause, visibility, and image lifecycle as WebGL.

`wallpaper-engine/property-spec.json` is canonical and `wallpaper-engine/project.json` is generated; do not hand-edit the latter. `scripts/wallpaper-engine/package.mjs` turns `dist/matrixcode.html` into the importable offline package and validates its contents. Continuous multi-display output relies on Wallpaper Engine's Span mode; separate web instances intentionally run independently because the host does not expose their virtual offsets.

## Native macOS screen saver

The macOS implementation is a separate AppKit + ScreenSaver.framework + Metal codebase in `macos/MatrixCodeScreenSaver`. It intentionally contains no TypeScript, HTML, WebGL, JavaScript runtime, or WKWebView. Keep it behaviorally aligned with the browser implementation:

- `MatrixCodeMetalView` renders the stationary-grid rain, glyph scrambling, bloom/glow-inspired compositing, themes, scanlines, vignette, overlap lanes, and continuous virtual-grid multi-display mode.
- `MatrixCodeRainLifecycle` mirrors the web intro/load ramp and glyph-distribution rules.
- `MatrixCodeIntroOverlayView` mirrors the typewriter intro, click/Escape skip behavior, timing, and token resolution.
- `MatrixCodeConfigurationController` is the native Options sheet for rain, intro, messages, and countdown/countup moments; settings are persisted with the same `mx-*` JSON keys and sanitization rules as the web app.
- `MatrixCodeTokenResolver` mirrors the web token grammar, including `{name}`, `{greeting}`, `{time}`, `{time:fmt}`, `{countdown}`, `{countup}`, and named countdown/countup moments.
- `MatrixCodeImageContract` and `MatrixCodeMetalView` mirror portable-mask sanitization/import, deterministic scheduling/placement, and falling-glyph reveal rendering. The native Images editor persists the same `mx-images` JSON document.

Any parity change should usually include tests in the web suite and the
corresponding native suites under `macos/MatrixCodeScreenSaver/Tests` and
`windows/MatrixCode/tests`.

## Native Windows app and screen saver

`windows/MatrixCode` is a separate C++20 implementation with no browser runtime:

- `MatrixCodeCore` contains the deterministic RGBA8 rain sim, Mulberry32 RNG, bounded frame stepping, controllers, settings sanitizers, compact image masks, and image scheduling/reveal math. Its golden fixtures are derived from the web source of truth.
- `MatrixCodeRenderD3D11` renders through an RGBA16F scene whose alpha channel carries the bloom signal, one to three Gaussian bloom levels, ACES tone mapping, scanlines, and vignette. A floating-point influence texture preserves the full HDR image-reveal range. DirectWrite builds the glyph atlas and the post-composite intro/HUD/toast surfaces; hardware D3D11 is preferred and WARP is the fallback/capture path.
- `MatrixCodeWin32` owns app and screen-saver lifecycle. `MatrixCode.exe` is the standalone host. `Matrix Code.scr` supports no-argument or `/c[:HWND]` configuration, `/s` full-screen playback, and `/p HWND` Control Panel preview. Full-screen mode coordinates one topmost window per physical monitor over one shared virtual-grid simulation.
- Settings are stored in `%LOCALAPPDATA%\MatrixCode\settings.json`. CMake builds `MatrixCodeNativeTests.exe` and `MatrixCodeRenderCapture.exe`; the PowerShell scripts under `windows/MatrixCode/scripts` configure, build, test, stage, sign, package, and verify.

Do not overstate Windows validation. The source implements the typed intro presentation, messages, image reveals, countdown tokens, structured document editors, WIC import, full 1.45 image brightness, per-display logical topology, and nonblocking multi-window presentation. A release claim still requires the MSVC native suite and WARP capture, x64 and ARM64 packaging, `.scr` shell-mode checks, and mixed-DPI/mixed-refresh hardware comparison. DirectWrite glyph pixels may vary with installed Windows fonts; keep that boundary documented in `windows/MatrixCode/README.md` and capture tolerances.

## Native Ubuntu app and XScreenSaver mode

The Ubuntu implementation under `linux/MatrixCode` is C++20 with Qt 6 Widgets
and OpenGL 3.3 Core. It compiles the portable `MatrixCodeCore` sources housed in
the Windows tree, so Linux and Windows share simulation, settings, scheduling,
image-reveal, token, holiday, controller, and topology behavior instead of
maintaining another translation.

- `MatrixCodeRenderGL` mirrors the RGBA16F scene, bloom tiers, ACES tone map,
  scanlines, vignette, glyph atlas, overlays, and adaptive-resolution contract.
- The Qt host owns the standalone, fullscreen, continuous multi-display,
  settings, structured editor, reduced-motion, pause, and capture lifecycles.
- `SettingsStoreLinux` persists the versioned `mx-*` snapshot atomically below
  the XDG configuration root, and `ImageImportQt` preserves the portable mask
  conversion rules.
- The application and multi-monitor presentation work on Wayland and X11.
  XScreenSaver embedding is X11-only. Stock GNOME Wayland does not provide a
  supported third-party secure lock-screen surface; do not bypass, patch, or
  weaken the system lock screen to simulate one.

Do not overstate Linux validation. Release claims require native arm64 and amd64
tests/packages, deterministic software capture comparison, NVIDIA and Mesa runs,
GNOME Wayland/X11 checks, mixed-DPI/mixed-refresh hardware, context recovery,
suspend/resume, monitor hot-plug, and `.deb` install/upgrade/uninstall tests.
System font pixels may vary; keep that boundary documented in
`linux/MatrixCode/README.md` and canonical capture tolerances.
